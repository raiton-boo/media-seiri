# 機能: 破損の検出と自動修復(repair)

## 1. 目的

壊れているファイルを検出し、可能なものは自動で修復を試みる。直らなかったものも、あとで復元できる可能性があるため、元のバイトのまま、ライブラリに残す。

## 2. 関連する要件

[破損・修復](../requirements.md#r-01)、[読み取れないファイル](../requirements.md#i-09)、[修復後も日付がない](../requirements.md#u-07)、[読み取り・修復が不可](../requirements.md#u-08)、[コピー専用](../requirements.md#c-03)
仕様書: §10-2, §10-3 / フロー: `flows.md` 5章

## 3. 方針

- 修復は、**「確実に直る」と約束するものではない**。試みて、結果を記録する。
- **元のファイルは、変更しない** ([コピー専用](../requirements.md#c-03)、[自動修復](../requirements.md#r-02))。修復したものは、別のファイルとして `repaired/` に作る。
- 3つの手順(動画の再構築、メタデータの再書込み、切れた画像の救出)を、すべて試す ([修復の 3 つの手順](../requirements.md#r-04))。

## 4. 破損の検出 (要件: [破損の検出](../requirements.md#r-01))

| 種別 | 検出の方法                                                   |
| :--- | :----------------------------------------------------------- |
| 画像 | デコードを試みて、途中で失敗するかを調べる                   |
| 動画 | メタデータとストリームの読み取りが、最後まで通るかを調べる   |
| RAW  | メタデータの読み取りと、埋め込みプレビューの読み取りを調べる |

- 「メタデータは読めるが、デコードは途中で失敗する」ものも、破損として扱う。
- メタデータが読めないことだけでは、破損としない(日付などの情報が取れないだけ。仕様書 §10-2)。
- 破損の程度(先頭だけ壊れている、末尾が切れている、など)を、可能な範囲で、記録する。

## 5. 修復の手順

| 順  | 手順                 | 対象       | 内容                                                                                     |
| :-- | :------------------- | :--------- | :--------------------------------------------------------------------------------------- |
| 1   | 動画の再構築         | 動画       | コンテナを作り直す(再エンコードはしない)。末尾が切れた動画の、インデックスの再構築を含む |
| 2   | メタデータの再書込み | 画像・動画 | 壊れたメタデータ部分を除いて、書き直す                                                   |
| 3   | 切れた画像の救出     | 画像       | 読み取れる範囲の画像データを、保存する                                                   |

- 各手順のあと、結果が読み取れるかを再検査する。読み取れたら、そこで終了する。
- 動画・画像の種類によって、試す手順が違う(図は、`flows.md` 5章)。
- 各手順の成否と、出力先を、`repair_attempts` に記録する。

## 6. 修復後の扱い

- 修復できたファイルは、「修復済み」の印を付けて、通常の取り込み(`ingest.md`)の流れに乗せる。
- 重複判定は、**修復後のハッシュ**で行う(修復で、元の内容と一致しなくなるため)。
- 修復後も、日付が取れなければ、`_unknown/修復後も日付なし/` に置く ([修復後も日付がない](../requirements.md#u-07))。
- 修復したファイルの元の場所は、元のソースのパスで記録する。`repaired/` の中のパスではない。

## 7. 修復できなかった場合 (要件: [読み取れないファイル](../requirements.md#i-09))

1. 修復の手順を 1 つ以上試して、直らなかったときは、`REPAIR_FAILED` を、エラー一覧に記録する(試した手順と理由を含む)。修復を試みなかったとき(dry-run、修復のツールが使えない、試行の上限を超えた)は、`CORRUPTED` を記録する(修復は未実施)。
2. バイトが読める場合は、**元のバイトのまま**、`_unknown/読み取り不可/` にコピーする(ハッシュ検証つき)。
   - いつか、別のツールで復元できる可能性があるため、残す。
3. バイト自体が読めない場合は、コピーできないので、エラー一覧にだけ記録する。

## 8. 見方(Web)

- エラー一覧で、`CORRUPTED`(修復は未実施)/ `REPAIR_FAILED`(修復を試みて失敗)を、絞り込める。1 つのファイルは、そのときの状態の 1 つだけが載る。
- ファイルごとに、試した手順と結果を表示する。
- `_unknown/読み取り不可/` のファイルは、サムネイルが作れないことがある。その場合は、プレースホルダーを表示する。

## 9. エッジケース

| 状況                                         | 振る舞い                                                                                               |
| :------------------------------------------- | :----------------------------------------------------------------------------------------------------- |
| 修復後のファイルが、元より小さい(一部を救出) | 「一部のみ救出」の印を付けて、記録する。(仮)                                                           |
| 修復のためのツールが使えない                 | 該当の手順を、スキップとして記録する。すべての手順をスキップした(1 つも試せなかった)ときは、`CORRUPTED` を記録する |
| 修復で、作業用の領域がいっぱいになる         | `COPY_FAILED` を記録して、その修復を中断する                                                           |
| 同じファイルを、再実行で再び修復する         | 前回の結果(`repair_attempts`)があれば、再試行せず、記録を使う。`--retry-repair` で、再試行できる。(仮) |

## 10. 受け入れ条件

- 破損したファイルが、検出されること。
- 修復の試行が、元のファイルを変更せず、`repaired/` に別ファイルとして作られること。
- 各手順の成否が、記録されること。
- 修復に成功したファイルが、通常の取り込みと同じ流れで、コピーされること。
- 修復に失敗したファイルが、エラー一覧に載り、バイトが読めれば、`_unknown/読み取り不可/` にコピーされること。
- 修復後も日付が取れないファイルが、`_unknown/修復後も日付なし/` に置かれること。
