# 技術選定

要件(`requirements.md`)・仕様書(`specification.md`)が固まったので、使う技術を選ぶ。
状態の凡例: **推奨** = 選定の結論(確認待ち) / **要確認** = 試作(PoC)で確かめる / **決定** = 合意済み。

### 1-1. 設計上の要点

**CLI と Web は、別々の配布形態でよい。**

- CLI は、この Mac だけで動く。ExifTool や ffmpeg などの外部ツールを、自由に使える。単体の実行ファイルにする必要はない。
- 単体の実行ファイルが必要なのは、**閲覧用の Web(ビューア)だけ**。この部分は、軽い(台帳を読んで、画面を出すだけ)。
- ただし、台帳(SQLite)のスキーマと型は、CLI と Web で共有する。

## 2. 言語・ランタイムの比較

| 観点                                                | Python                                                            | Go                             | **TypeScript(Bun)**                                          | Rust |
| :-------------------------------------------------- | :---------------------------------------------------------------- | :----------------------------- | :----------------------------------------------------------- | :--- |
| ビューアを、OS ごとの単体の実行ファイルにする       | △ OS ごとに、その OS 上でビルドが要る(Windows 機または CI が必要) | ◎ 簡単に、他の OS 向けを作れる | ○ 他の OS 向けのビルドに対応(Windows・macOS)                 | ◎    |
| 画面(React)と同じ言語                               | ×                                                                 | ×                              | ◎ 型・検証を共有できる                                       | ×    |
| これまでの慣れ(TS・React・Biome)                    | △                                                                 | ×                              | ◎                                                            | ×    |
| 開発の速さ                                          | ◎                                                                 | ○                              | ◎                                                            | △    |
| 読み書き・ハッシュの性能                            | ○                                                                 | ◎                              | ○(読み書きが律速のため、実用上は十分)                        | ◎    |
| macOS の `F_NOCACHE`(キャッシュを避けた読み出し)    | ○ 標準ライブラリで呼べる                                          | ◎ 容易                         | △ 標準では呼べない。`bun:ffi` で OS の関数を呼ぶ必要(要確認) | ◎    |
| 写真・動画・メタデータの周辺(ExifTool、ffmpeg 連携) | ◎                                                                 | ○                              | ○                                                            | ○    |
| ライブ表示の CLI                                    | ◎(Rich)                                                           | ◎(Bubble Tea)                  | ○(Ink など)                                                  | ○    |
| SQLite                                              | ◎                                                                 | ○                              | ◎ Bun に内蔵                                                 | ○    |
| 画面と CLI を、1 つのリポジトリで管理               | △                                                                 | △(言語が 2 つ)                 | ◎                                                            | △    |

### 2-1. 結論(推奨)

**TypeScript を、Bun で動かす。**

- 実行ファイルの配布(ビューア)が、他の OS 向けにも作れる。Bun は、`--compile` で単体の実行ファイルを作れ、Windows・macOS(arm64 / x64)向けを、別の OS からビルドできる([Bun のドキュメント](https://bun.com/docs/bundler/executables))。SQLite の組み込み(`bun:sqlite`)や、ファイルの同梱にも対応している。
- 画面(React)・CLI・サーバーが、すべて TypeScript。台帳の型や、エラーのコードを共有できる。
- これまでのプロジェクトと同じ道具(Biome、Next.js、Tailwind)で、[`CODING-STYLE.md`](rules/CODING-STYLE.md) の規約を、そのまま満たせる。

### 2-2. 懸念と、その対処

| 懸念                                                                     | 対処                                                                                                                             |
| :----------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------- |
| `F_NOCACHE` を、TypeScript から呼べるか                                  | `bun:ffi` で OS の `fcntl` を呼ぶ。**PoC で確認済み**(§10-5。書き込みの時点から付ける必要がある)                                 |
| 実行ファイルの大きさ(ランタイムを同梱するため、数十〜100MB 規模の見込み) | 2TB のドライブには、十分に小さい。OS ごとに 1 つずつ置く                                                                         |
| Bun の成熟度                                                             | ビューアは、台帳を読むだけの単純な構成。Windows の実機では、システムが全部できたあとの受け入れ確認で確かめる(§10-3)              |
| 性能が足りない場合                                                       | 重い処理(ハッシュ・コピー)だけを、別の実行ファイルに切り出す余地を残す。ビューアと CLI の中核を、Go に置き換える案を、予備にする |

### 2-3. 他の候補を選ばなかった理由

- **Python**: 開発は速いが、ビューアの単体の実行ファイルが、OS ごとのビルドを要する。家の PC が Windows なら、ビルド用の環境が別に要る。
- **Go**: 配布・性能は最良。ただし、画面は結局 TypeScript で書くので、言語が 2 つになる。これまでの慣れとも合わない。TypeScript で、PoC が失敗した場合の、**第一の予備**とする。
- **Rust**: 性能は高いが、開発の速さと慣れで、不利。

### 3-1. Next.js の使い方(決定)

- **静的書き出し(`output: 'export'`)で使う。** 画面は、すべて、ブラウザ側で描画し、データは、Hono の API から取得する。
- **`use cache` / Cache Components / Partial Prerendering(PPR)は、使わない。** これらは、サーバーが要り、静的書き出しに対応していない([参考](https://mcpservers.org/agent-skills/vercel/openreview/next-cache-components))。家の PC に配る、単体の実行ファイルとは、両立しない。データも、ローカルの SQLite から、API で取得するだけで、サーバー側のキャッシュの利点は、小さい。
- **Suspense は、使う。** React の標準の機能で、画面側の「読み込み中」のスケルトンに使える。TanStack Query(Suspense モード)と組み合わせる。
- 静的書き出しで使えない機能(要サーバー)は、使わない: `generateStaticParams` のない動的ルート、Cookie、リダイレクト、リライト、ISR など([参考](https://nextjs.org/docs/app/building-your-application/deploying/static-exports))。**年・月・できごとなど、可変の URL は、クエリ文字列と、画面側のルーティングで表す。**
- 「Mac だけ、サーバーとして動かして `use cache` を使う」案は、画面が 2 通りになるため、採らない。

## 4. ハッシュのアルゴリズム (要件: [SHA-256](requirements.md#h-05))

| 候補        | 速度                               | 特徴                                                                                               |
| :---------- | :--------------------------------- | :------------------------------------------------------------------------------------------------- |
| **SHA-256** | Apple Silicon では、専用命令で高速 | **標準のコマンド**(`shasum -a 256`、Windows の `Get-FileHash`)で、ツールなしに、独立して検証できる |
| BLAKE3      | とても高速                         | 標準のコマンドにはない。専用のライブラリが要る                                                     |
| xxHash3     | とても高速                         | 暗号用ではない。独立した検証の手段が少ない                                                         |

### 推奨: SHA-256

- このツールの律速は、**ドライブの読み書き(USB の HDD で、約 60〜100MB/s)**。ハッシュの計算は、それより、はるかに速いので、BLAKE3 の速度の利点は、実際には現れない。
- 一方で、**ツールを使わずに、独立して検証できる**ことは、「転送中の破損を確実に見つける」という目的に、直接役立つ(例: 家の Windows PC で、ライブラリの一部を、標準の機能で確かめられる)。
- 重複判定の識別にも、十分(衝突の心配は、実質ない)。

## 5. 外部ツールの扱い(この Mac だけ)

| ツール           | 用途                               | 導入                                                               |
| :--------------- | :--------------------------------- | :----------------------------------------------------------------- |
| ExifTool         | メタデータ(日時・GPS・カメラ)      | `exiftool-vendored` が、本体を同梱する(別途の導入は、不要の見込み) |
| ffmpeg / ffprobe | 動画の修復・サムネイル・破損の検査 | Homebrew で導入(**導入済み**。ffmpeg 9.0.2)                        |
| sips             | HEIC・RAW の変換                   | macOS に標準で入っている                                           |

- 導入は、実装の段階で、承認を得て行う([`AI-GUIDELINES.md`](rules/AI-GUIDELINES.md) の、パッケージの追加の規定)。
- 外部ツールが見つからない場合は、起動時に、不足を分かりやすく表示して止める。

## 6. リアルタイム更新(CLI → Web)

- CLI が、台帳(SQLite、WAL)に書き込み、Web のサーバーが、同じファイルを読み取る。
- Web は、新しいイベントを、**SSE** で画面に流す(`events` を、最後に読んだ番号から読み進める)。
- WAL なので、書き込み中でも、読み取りは止まらない。
- 別のプロセス間の通知(書き込みがあったことの通知)は、まず、短い間隔の確認(ポーリング)で始め、必要なら、ファイルの更新通知に変える。(仮)

## 7. 地図 (要件: [オンラインの地図タイル](requirements.md#c-11))

### 7-1. 地図のライブラリ

| 候補                     | 評価                                                                                                                                                                                      |
| :----------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **MapLibre GL JS(推奨)** | クラスタの機能を内蔵(Supercluster)。数万件以上でも軽く、滑らかな拡大・縮小ができる([参考](https://blog.mapbox.com/clustering-millions-of-points-on-a-map-with-supercluster-272046ec5c97)) |
| Leaflet + MarkerCluster  | 導入は簡単。件数が多い(数万件〜)と、重くなる傾向                                                                                                                                          |
| OpenLayers               | 高機能だが、導入が重い                                                                                                                                                                    |

- ピンの件数は、数万〜10 万件になりうる(`map.md` 8章)ので、MapLibre GL JS を推奨する。

### 7-2. タイルの提供元(設定で変更可能にする)

| 提供元                             | 範囲     | 条件                                                                                                                                                                                                             |
| :--------------------------------- | :------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **国土地理院の地理院タイル**       | 日本国内 | 地理院サーバーのタイルを、リアルタイムで読み込んで表示する場合は、**申請不要で、出典の明示だけ**で利用できる([国土地理院](https://www.gsi.go.jp/LAW/2930-qa.html))                                               |
| OpenStreetMap の公式タイル         | 世界     | 通常の閲覧の範囲なら可。ただし、**範囲を指定した事前の取得(オフライン用)や、過度な利用は禁止**。ブロックされることがある([利用ポリシー](https://operations.osmfoundation.org/policies/tiles/))。出典の表記が要る |
| 鍵が必要な提供元(無料枠のあるもの) | 世界     | 鍵(API キー)は、環境変数で与える([`CODING-STYLE.md`](rules/CODING-STYLE.md) の規約)。条件は、各社の規約で確認する                                                                                                |

- **決定した初期構成**: 国土地理院の地理院タイルだけを、既定にする。撮影場所が、日本国内だけのため。OpenStreetMap は、設定で選べる任意の提供元として残す(通常の閲覧のみ)。海外の写真が出てきたら、設定で切り替える。
- 本ツールの利用は、個人で、地図を閲覧するだけ。事前の取得や、まとまった取得は、しない。
- **要確認(PoC)**: ローカルのアプリ(`127.0.0.1`)から、OpenStreetMap の公式タイルを使う場合の、扱い(送られる参照元などの条件)。使えない場合は、鍵が必要な提供元に切り替える。
- 出典の表記(著作権表示)を、画面に出す。

## 8. ビューアの配布(家の PC 向け) (要件: [単体の実行ファイル](requirements.md#w-02))

### 8-1. 構成

```text
<ドライブ>/
├── Pictures/            ← ライブラリ
└── viewer/
    ├── file-seiri-viewer-mac-arm64
    ├── file-seiri-viewer-windows-x64.exe
    └── README.txt       ← 起動の手順
```

- 画面(React のビルド結果)と、サーバー(Hono)と、SQLite の読み取りを、**1 つの実行ファイルに同梱**する。
- ビルドは、この Mac で、Windows 向け・macOS 向けを、作る(Bun の他の OS 向けのビルド)。
- 起動すると、実行ファイルの場所から、ライブラリを探し、ブラウザを開く。

### 8-2. 要確認(PoC)

- 家の Windows PC で、実行できること(セキュリティの警告の表示を含む。署名のない実行ファイルは、警告が出うる)。
- ExFAT のドライブ上で、台帳を読み取り専用で開けること。
- 画面の静的ファイルが、実行ファイルから配信されること。

### 8-3. 署名について

- 署名のない実行ファイルは、Windows・macOS で、初回に警告が出ることがある。個人利用なので、警告を許可して使う前提とする。(`README.txt` に手順を書く)

## 9. Docker の採否 (要件: [Docker は使わない](requirements.md#c-10))

**使わない(推奨)。**

- 取り込みは、外付けドライブの直接の読み書き、OS のキャッシュを避けた読み出し(`F_NOCACHE`)、`sips` などの、Mac の機能を使う。コンテナを挟むと、ドライブの読み書きが遅くなりやすく、これらが使えない。
- 家の PC では、Docker を入れる必要がない(Windows では、重い)。単体の実行ファイルで足りる。
- 必要になったら、ビューアだけの Dockerfile を、あとから追加できる(スコープ外)。

### 10-1. PoC #8 の結果(2026-10-18、この Mac)

試作のコードは、`poc/viewer-embed/` に置いた(使い捨て。本実装には使わない)。

| 項目                     | 結果                                                                                                   |
| :----------------------- | :----------------------------------------------------------------------------------------------------- |
| 画面・API・404           | 画面(HTML)・API・存在しないパスの 404 が、想定どおりに動いた。画面は、再読み込みしても、すぐ表示された |
| 同梱したファイル         | 26 個(728KB)                                                                                           |
| 実行ファイルの大きさ     | macOS 用 68MB / Windows 用 93MB                                                                        |
| 実行ファイルだけで動くか | 動いた(`/tmp` に移して、`out/` なしで確認)                                                             |
| Windows 用の実行ファイル | 作れた(`PE32+ executable, x86-64`)。**Windows の実機での実行は、未確認**(PoC #2 で行う)                |

分かったこと(本実装に引き継ぐ)。

1. `bun build --compile` では、`with { type: "file" }` の import で、静的ファイルを実行ファイルに同梱できる。ファイルが多いので、import の一覧は、スクリプト(`gen-assets.ts`)で自動生成する。
2. 自動生成のファイルは、`.js` を「モジュール」、`.html` を「HTMLBundle」と、TypeScript が誤って推論する(実行時は、Bun が、パスの文字列として扱う)。`// @ts-nocheck` で、型の検査から外し、理由をコメントに書く。
3. `next build` の型の検査は、`src/` も対象にする。ビルドの順序(`next build` → 一覧の生成 → 実行ファイルの作成)で、一覧のファイルが、最初のビルドの時点で、存在しない。空の初期ファイルを置くか、ビルドの手順をスクリプトにまとめる。
4. `next build` は、`tsconfig.json` を、配列を複数行にして書き換える。Biome の整形と食い違うので、ビルドのあとに `biome check --write` を実行する。
5. 試作で、`bun build --compile` の出力先が、入れ子のフォルダ(`dist/viewer-mac./dist/viewer-mac`)になったことがあった。同じ指定の再現テストでは、普通に 1 ファイルができた。原因は、特定できていない(入力したコマンドの違いの可能性が高い)。ビルドのあとは、`ls` で、実行ファイルが 1 ファイルとしてできたことを確認する。

分かったこと(本実装に引き継ぐ)。

1. `bun:ffi` で、`fcntl(F_NOCACHE)`(定数 48)を呼べる。**読むときにだけ付けても、すでにキャッシュにあるデータは、キャッシュから返る**。書き込みの時点から付ける(仕様書 §7)。
2. exFAT では、macOS が、書いたファイルごとに、`._名前`(AppleDouble、4KB)の付属ファイルを作る。書いたあとに削除すれば、本体は無事で、作り直されない。`dot_clean` でも消せる。`xattr -d` は効かない(仕様書 §7)。
3. exFAT のドライブでは、`rmSync` の再帰の削除が、最初の 1 ファイルだけを消して、エラーなしに止まる。先に一覧を作って、1 つずつ消し、消えたことを確かめる。
4. 読み書きの単位は、4〜64MiB で差が出なかった。ファイル 1 つごとの手間(`open`・`fsync`・名前の変更・付属ファイルの削除)が支配的。
5. 全件(約 124GB)のコピー + 検証は、約 55 分の見込み。複数ファイルを重ねて処理する並列の効果は、未測定。

```text
file-seiri/
├── docs/

│   ├── core/       ← 台帳のスキーマ・型・日付の決定・命名の規則(CLI と Web が共有)
```
