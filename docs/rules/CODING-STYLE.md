# コーディング規約 (Coding Guidelines)

本規約は、コードの可読性と保守性を高め、属人性を排除することを目的とする。
フォーマットなどの「機械が判断できること」はツールに任せ、人間（とAI）は「設計と意図」に集中する。

## 要点

- Linter・Formatter を必ず使い、警告は解消してからコミットする。
- 命名は、何をするものかが分かる英単語にする。コメントは「なぜ」を日本語で書く。
- エラーを握りつぶさない。`any` と機密情報のハードコードは使わない。

---

## 1. フォーマットと静的解析 (Linter / Formatter)

- **ツールの強制**: プロジェクトごとに指定された Linter (例: ESLint) と Formatter (例: Prettier) を必ず使用する。言語ごとのツールは「8. 言語別の差分」を参照する。
- **警告のゼロ化**: Linter のエラーや警告は原則すべて解消してからコミットする。やむを得ずルールを無効化（disable）する場合は、必ずコメントで理由を明記する。

---

## 2. 命名規則 (Naming Conventions)

- **明確さを優先**: 短さよりも「何をするものか」が正確に伝わる英単語を選ぶ。（例: `d` ではなく `userData`）
- **真偽値 (Boolean)**: `is`, `has`, `should`, `can` などの接頭辞をつける。（例: `isVisible`, `hasError`）
- **関数名**: 実行する処理が分かるように「動詞」から始める。（例: `getUser`, `calculateTotal`）
- **ローマ字を使わない**: 識別子は英語にする。（例: `yuuzaa` ではなく `user`）
- **コレクションは複数形**: 配列や一覧は複数形、単体は単数形にする。（例: `users` と `user`）
- **ケースの統一**: 言語やフレームワークの標準的な慣習に従う（例: JS/TSの変数は `camelCase`、コンポーネントは `PascalCase` など）。

---

## 3. 実装のベストプラクティス

- **早期リターン (Early Return)**: ネスト（インデント）を浅く保つため、異常系や条件を満たさない場合は、関数の冒頭で先に `return` する（ガード節）。
- **マジックナンバーの禁止**: 意味のある数値や特定の文字列は、コード内に直接書かずに「定数」として定義し、名前を与える。
- **単一責任の原則 (SRP)**: 1つの関数やファイルは、1つの役割だけを持つようにする。処理が長くなりすぎた場合は、適切に分割を検討する。

| ルール                 | OK                                                  | NG                                      |
| :--------------------- | :-------------------------------------------------- | :-------------------------------------- |
| 早期リターン           | `if (!user) return;` を先頭に書き、本処理を浅くする | 本処理を `if (user) { ... }` で包む     |
| マジックナンバーの禁止 | `const MAX_RETRY = 3;` を使う                       | `if (count > 3)` と直接書く             |
| 単一責任               | 取得・整形・表示を、別の関数に分ける                | 1つの関数に、取得から表示までを詰め込む |

---

## 4. コメントと Docstring の書き方

- **Docstring**: 処理を読んだだけでは挙動が伝わりにくい関数や複雑なロジックには、目的・引数・戻り値を説明するコメントや Docstring（JSDoc, Python Docstringなど）を必ず書く。
- **コメントは「なぜ」を書く**: 読めば自明な処理（What）を、行ごとにコメントしない。代わりに、「なぜそのアプローチをとったのか」「なぜその制約・数値を設定したのか」といった背景を書く。
- **日本語で書く**: コメントと Docstring は日本語にする。識別子（変数名・関数名など）は従来どおり英語とする。
- **コメントアウトしたコードを残さない**: 使わなくなったコードは削除する。過去の内容が必要な場合は、Gitの履歴から復元する。例外: 一時的に残す必要がある場合は、`TODO:` を付けて、「残す理由」と「削除する条件」を明記する。
- **TODO / FIXME**: 後で対応が必要な箇所や、一時的なハックコードには、`TODO:` や `FIXME:` を付けて、何をすべきか明記する。

---

## 5. エラーハンドリング (Error Handling)

- **エラーの握りつぶし禁止**
  - `catch` ブロックなどを空にして、発生したエラーを隠蔽する（サイレントエラー）ことを固く禁じる。
- **適切な処理と伝播**
  - エラー発生時は適切なログ出力を行い、必要に応じて呼び出し元へエラーを伝播させて適切に処理されるようにする。

---

## 6. 型の安全性 (Type Safety)

- **`any`の原則禁止**
  - 型のある言語（TypeScriptなど）を使用する場合、型安全性を損なう `any` 型（またはそれに準ずるもの）の使用は原則禁止とする。型が決まらない値は、TypeScript では `any` の代わりに `unknown` を使い、型を絞り込んでから扱う。
- **境界の型定義**
  - 内部処理では型推論を活かしつつ、APIのレスポンスや外部モジュールとの境界部分には明示的に型（インターフェース）を定義し、データ構造を保証する。

---

## 7. セキュリティと機密情報 (Security & Secrets)

- **ハードコードの厳禁**
  - APIキー、パスワード、認証トークンなどの機密情報をソースコード内に直接記述（ハードコード）してはならない。
- **環境変数の利用**
  - 機密情報や、環境（開発・本番）ごとに変わる設定値は、必ず環境変数（`.env` 等）を経由して読み込むこと。
- **ログへの出力禁止**
  - パスワードや認証トークンなどの機密情報を、ログに出力してはならない。

---

## 8. 言語別の差分

共通の原則（1〜7）は全言語に適用する。言語によって異なる点のみ、以下で定める。

| 項目             | Python             | PHP                | Go                                        | TypeScript (JS)       |
| :--------------- | :----------------- | :----------------- | :---------------------------------------- | :-------------------- |
| 変数・関数       | `snake_case`       | `camelCase`        | 非公開は `camelCase`、公開は `PascalCase` | `camelCase`           |
| クラス・型       | `PascalCase`       | `PascalCase`       | `PascalCase`                              | `PascalCase`          |
| 定数             | `UPPER_SNAKE_CASE` | `UPPER_SNAKE_CASE` | 非公開は `camelCase`、公開は `PascalCase` | `UPPER_SNAKE_CASE`    |
| Docstring の書式 | Google スタイル    | PHPDoc             | godoc                                     | TSDoc                 |
| Formatter        | Black              | Pint               | gofmt                                     | Biome または Prettier |
| Linter           | Ruff               | PHPStan            | golangci-lint                             | Biome または ESLint   |
| 準拠する標準     | PEP 8              | PSR-12             | Effective Go                              | －                    |

- Python は Ruff を Linter 専用で使う（整形は Black に任せる）。
- 「6. 型の安全性」は TypeScript が対象。JavaScript は JSDoc で型を補う。
- Go では `any` / `interface{}` を「6」の `any` 禁止の対象とし、`_ = err` によるエラーの無視を「5」の握りつぶしとみなす。
