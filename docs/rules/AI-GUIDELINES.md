# AI・コーディングアシスタント規約 (AI Coding Guidelines)

本規約は、AIアシスタント（Cursor, Claude Code, GitHub Copilot等）を効果的かつ安全に活用し、意図しない事故を防ぎながら開発効率を向上させることを目的とする。

## 要点

- 最終責任は人間にある。AIの生成物は、人間が検証してから適用・コミットする。
- ファイルの編集や、状態を変える操作は、人間から明示的に依頼されたときだけ行う。調査・確認は、承認なしで行ってよい。
- 破壊的変更は、依頼されていても、影響範囲を示して再確認を得てから行う。
- APIキーやパスワードなどの機密情報は、プロンプトに入力しない。

---

## 1. 基本方針・責任範囲

- **最終責任は人間にある**: AIが生成・編集したコードやコマンドは、必ず人間が内容を検証した上で適用およびコミットを行う。
- **ワンショットでの大規模変更の禁止**: AIに一度で大量のファイルを変更させず、小さな単位で段階的に生成・検証を行う。
- **設計意図・方針の事前説明（必須）**: AIはコードの生成や大幅な編集を行う前に、必ず提案する実装方針や設計意図を一度人間に説明・確認した上で、コードを出力する。大幅な編集とは、複数ファイルにまたがる変更や、既存の動作を変える変更をいう。誤字の修正や、1ファイル内の軽微な修正は、方針の説明を省いてよい。

---

## 2. 権限・操作ルール

AIアシスタントに付与する権限は、「調査・確認」と「編集・実行」で厳格に区別する。

### 2-1. 事前承認が必要な操作

以下は、人間（開発者）から明示的に依頼された場合のみ許可する。依頼されていないタイミングでの自主的な編集・実行は禁止する。

| 操作                                          | 内容                                                                                                                                                     |
| :-------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ソースファイルの編集・書き込み (Write / Edit) | 「〇〇機能を代わりに実装して」「このバグを修正して」と指示された場合のみ、対象範囲の編集を許可する。                                                     |
| 状態を変更するコマンドの実行                  | Git操作（`git commit`, `git push` 等）、GitHub CLI（`gh pr create` 等）、パッケージの追加・更新、各種デプロイや設定変更コマンドなど。                    |
| 曖昧な言い方への対応                          | 「〜したい」「〜しておきたい」のように、依頼か、本人が行う意思表示か判断できない言い方は、依頼とみなさない。実行せず、「私が実行してよいか」を確認する。 |
| 外部への書き込み・送信                        | Issue・PR・コメントの投稿、メールやチャットへの送信、外部サービスへの公開など。取り消しにくいため、内容を示して承認を得てから実行する。                  |

### 2-2. 承認なしで行える操作

プロジェクトの構造把握や原因究明をスムーズに行うため、以下は、人間の事前承認なしで実行・参照してよい。

- **読み取り専用のアクセス**: ディレクトリ構造の確認、ファイル・フォルダの読み込み、設定の参照、コードの静的解析など（機密ファイルを除く。「3. セキュリティと機密情報」参照）。
- **調査・確認目的のコマンド実行**: ログの出力確認、エラー調査、ビルドやテストの事前確認など、ファイルやリポジトリ・外部環境の状態を変更しないコマンド。
- **一時的なデバッグコードの挿入**: 2-1 の例外として、原因調査のために、ログ出力用のコード等を一時的に書き込んでよい。ただし、調査完了後は、必ず元通りに削除（クリーンアップ）する。

### 2-3. 破壊的変更の事前確認

次の「破壊的変更」を行う可能性がある場合は、人間から依頼された操作であっても、影響範囲を提示し、明示的な再確認を得てから実行・編集する。

- 既存機能の削除、大幅なリファクタリング、スキーマや構造の非互換な変更
- ファイルやディレクトリの削除・移動
- 破壊的なコマンドの実行（`git reset --hard`, `git push --force`, DBドロップ等）

例外: スタックPRと親ブランチ方式の更新は、人間が更新を依頼した場合に限り、その作業ブランチへの `git push --force-with-lease`（`gh stack sync` / `gh stack rebase` / `gh stack submit` を含む）を、再確認なしで実行してよい。`main` や他の人のブランチへの強制pushは、引き続き禁止する（[PR.md](./PR.md#6-スタックprgh-stack方式) 参照）。

## 3. セキュリティと機密情報

- **機密情報の入力禁止**: APIキー、パスワード、DB接続情報などのクレデンシャルは、絶対にプロンプトやチャットツールに入力しない。
- **機密ファイルの読み取り禁止**: `.env`、秘密鍵、認証情報のファイルは、内容を開いて読まない。非機密の値だけが必要で、キー名が分かっている場合に限り、そのキーだけをコマンドで取得してよい（例: `grep '^PORT=' .env`）。パスワードやトークンなどの機密の値は、取得しない。
- **個人情報・環境情報の保護**: 実際のユーザーデータや機密性の高い情報は含めず、必要に応じてダミーデータに置き換えて質問する。

---

## 4. クリーンネスと品質管理

- **既存ルールの遵守**: プロジェクト内のブランチ戦略、コミット規約、コーディング規約（Linter / Formatter等）に従った挙動を維持させる。
- **不要なコードの削除**: AIが生成した不要なコメントや、デバッグ用のコード（`console.log`, `print` 等）は、PR提出前にすべて削除する。
- **AIの署名を残さない**: コミットメッセージやPR本文などに、`Co-Authored-By` や、AIが生成したことを示す表記を付けない。
