# 📝 コミットメッセージ規約 (Commit Message Conventions)

履歴の可読性を高めるため、**「1行で完結する」**プレフィックス型のコミットメッセージを採用する。

## 1. 基本フォーマット

    <type>: <subject>

- **`type`**: コミットの種類（ブランチの接頭辞と完全に一致させる）
- **`subject`**: 変更内容の簡潔な要約
- **【重要】** `:` (コロン) の後ろには必ず半角スペースを1つ空けること。

---

## 2. プレフィックス (Type) 一覧

| Type            | 用途                                       | コミットメッセージの例                       |
| :-------------- | :----------------------------------------- | :------------------------------------------- |
| **`feat:`**     | 新機能の追加                               | `feat: ユーザー認証機能を追加`               |
| **`fix:`**      | バグ修正                                   | `fix: スマホ画面のレイアウト崩れを修正`      |
| **`hotfix:`**   | 本番の緊急バグ修正                         | `hotfix: 決済APIのエラーを修正`              |
| **`refactor:`** | リファクタリング（機能追加やバグ修正なし） | `refactor: ログインロジックの共通化`         |
| **`chore:`**    | ツール設定、パッケージ更新、雑務           | `chore: 依存パッケージのアップデート`        |
| **`docs:`**     | ドキュメントの追加・修正                   | `docs: READMEにセットアップ手順を追記`       |
| **`test:`**     | テストの追加・修正                         | `test: ログインバリデーションのテストを追加` |
| **`ci:`**       | CI/CD（GitHub Actions等）の変更            | `ci: 本番デプロイ用のワークフローを追加`     |

---

---

## 3. ベストプラクティス

- **1コミット ＝ 1つの関心事（Single Concern）**
  - 関心事ごとにコミットを分けること。新機能の追加（`feat`）とリファクタリング（`refactor`）など、複数の関心事を1つのコミットに混ぜない。
- **基本は1行で完結させる**
  - 背景や詳細な理由はPR（Pull Request）の概要欄に記載する。
- **Issueとの紐付け（PRを使わない場合）**
  - 通常はPR本文に `Closes #12` と書いて自動クローズする。
  - ただしPRを作成せず直接メインブランチへPushする場合など、PRを経由しない状況でIssueを自動クローズしたい時は、コミットメッセージ末尾に `Closes #12` を含めてよい（例: `docs: READMEを更新 Closes #12`）。
- **Gitコマンドの指定 (`git checkout` の禁止)**
  - 役割の混同を防ぐため `git checkout` の使用は禁止とし、ブランチ切り替えには `git switch`、ファイルの復元・取り消しには `git restore` を使用する。
