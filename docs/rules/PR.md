# プルリクエスト規約 (Pull Request Guidelines)

本規約は、コードレビューの負担を減らし、変更の意図と影響範囲をチーム（および未来の自分）に正確に伝えることを目的とする。

## 要点

- 1 PR＝1目的。サイズはできるだけ小さく保つ。
- 作成時に、Assignees へ自分（`@me`）を設定する。
- タイトルは `feat: ログイン画面のUI実装` のように、プレフィックスを付ける。
- `main` へのPRは `Closes #xx`、それ以外は `Refs #xx` と書く。
- 本番の緊急バグ修正（`hotfix`）は、[7. hotfix](#7-hotfix本番の緊急バグ修正) の手順に従う。

---

## 1. PR作成時の基本ルール

- **1 PR＝1目的**: PRのサイズはできるだけ小さく保つ。「新機能の追加」と「無関係なリファクタリング」は別のPRに分ける。
- **アサイン（必須）**: 責任の所在を明確にするため、作成時は必ず Assignees に自分自身（`@me`）を設定する。レビューが必要な場合は、適切な Reviewers も設定する。
- **セルフレビュー**: レビューを依頼する前に、Files changed（差分）を自分で確認し、不要なファイルやデバッグ用のコード（`console.log` や `dd()` など）が含まれていないかチェックする。
- **タイトル**: コミットメッセージ規約と同様にプレフィックス（`feat:`, `fix:` など）を使い、何を変更したかが一目でわかるようにする。

| OK                           | NG                                 | 理由                     |
| :--------------------------- | :--------------------------------- | :----------------------- |
| `feat: ログイン画面のUI実装` | `ログイン画面のUI実装`             | プレフィックスがない     |
| `fix: ヘッダーの崩れを修正`  | `fix: いろいろ修正`                | 何を変えたかが分からない |
| `feat: ログイン画面を追加`   | `feat: ログイン追加とヘッダー整理` | 複数の目的が混ざっている |

---

## 2. PRの概要 (Description) とテンプレート

PRの本文は、以下のテンプレート（`.github/pull_request_template.md` に設定推奨）を使用して記載する。

```markdown
## 概要

<!-- 何を、なぜ変更したか -->

## 動作確認

- [ ] Linter・自動テストをクリアした
- [ ] ローカル環境で〇〇が正常に動作することを確認した

## 関連Issue

<!-- mainへのPR: Closes #xx / それ以外: Refs #xx -->
```

### 関連Issueの書き方

PR作成時、本文の「関連Issue」に `Closes #Issue番号`（例: `Closes #12`）と書くと、PRのマージ時に該当のIssueが自動的にクローズされる。

自動クローズされるのは、`main` へマージされるときだけである。

- `main` 以外をベースにするPR（親ブランチやスタックの途中のPRなど）に `Closes` を書いても、Issueは閉じない。そのため、このPRには `Refs #Issue番号` と書く。
- `Closes` は、`main` にマージされるPRの本文にまとめて書く（[5. 親ブランチ方式](#5-親ブランチ方式) 参照）。
- 作業ブランチ間のマージでもIssueを自動クローズしたい場合は、`.github/workflows/` にGitHub Actionsのワークフローを用意する。

---

## 3. マージ方式について

マージ実行時は固定の方式に限定せず、PRの性質や変更の規模に応じて最適な方式を使い分ける。迷ったときは、Squash and Merge を使う。

| 方式                  | 向く場面                             | 履歴の残り方                                         | revertのしやすさ           |
| :-------------------- | :----------------------------------- | :--------------------------------------------------- | :------------------------- |
| Squash and Merge      | 小〜中規模な機能追加・バグ修正       | 1PR＝1コミットにまとまり、履歴をシンプルに追える     | PR単位で戻しやすい         |
| Create a merge commit | 大規模機能開発・複数人での共通開発   | 全コミットとマージコミットが残り、過程が細かく分かる | マージコミット単位で戻せる |
| Rebase and Merge      | リファクタリング・独立したコミット群 | マージコミットを作らず、全コミットが直線状に残る     | コミット単位で戻せる       |

---

## 4. 大きな変更を分けて出す方法（適材適所）

1つのPRではレビューしにくい大きな変更は、小さなPRに分けて出す。方法は次の2つで、どちらも選択肢の1つ。状況に応じて使い分ける。変更が小さい場合は、どちらも使わず単独のPRにする。

| 方式                                                           | 形                                   | `main` に入る時期                        |
| :------------------------------------------------------------- | :----------------------------------- | :--------------------------------------- |
| [親ブランチ方式](#5-親ブランチ方式)（5章）                     | 親の下に子が並ぶ（子は互いに独立）   | 機能が完成してから、親をまとめて入れる   |
| [スタックPR](#6-スタックprgh-stack方式)（`gh stack`方式・6章） | 一列に積む（前のブランチに依存する） | 下の段から順に、レビューが済み次第入れる |

### 使い分けの例

| 状況                                                           | 向く方式                 |
| :------------------------------------------------------------- | :----------------------- |
| ロジックを作ってから、それを呼ぶ画面を作るなど、順番に依存する | スタックPR               |
| ロジック・画面・リファクタリングを並行して進められる           | 親ブランチ方式           |
| 機能が完成するまで `main` に入れたくない（途中だと動かない）   | 親ブランチ方式           |
| 小さく早く `main` に入れていきたい                             | スタックPR               |
| 変更が小さく、1つのPRで済む                                    | どちらも使わず、単独のPR |

## 5. 親ブランチ方式

機能全体の「親ブランチ」を作り、そこから「子ブランチ」を切って小さなPRに分ける。`gh stack` は使わない。

```text
main ← feat/login (親)
          ├─ feat/login-logic     (子: ロジック)
          ├─ feat/login-ui        (子: 画面)
          └─ refactor/login-form  (子: リファクタリング)
```

1. 切り元（`main`、または他の作業ブランチ）から親ブランチを切る。
2. 親ブランチから子ブランチを切る。
3. 子ブランチのPRは、**ベースを `main` ではなく親ブランチ**にして出し、親ブランチへマージする。
4. 子のPRはそれぞれ独立していて、マージ順は問わない。
5. すべての子をマージしたら、親ブランチから切り元へのPRを出す。

- 親ブランチは、すべての子がマージされ、切り元へのPRがマージされるまで削除しない。
- **関連Issue:** 子のPRには `Refs #xx` と書き、親から `main` へのPRの本文に `Closes #xx` をまとめて書く（例: `Closes #1, Closes #2`）。原則は [関連Issueの書き方](#関連issueの書き方) を参照。
- 子のPRを親へマージする方式は、[3. マージ方式](#3-マージ方式について)から選ぶ。
- 子の作業中に親ブランチが進んだ場合は、子ブランチに親の変更を取り込む（`git rebase <親ブランチ>` または `git merge <親ブランチ>`）。

## 6. スタックPR（`gh stack`方式）

前のブランチを土台にした小さなPRの連なり（スタック）に分けて出す。
`gh stack` を使うと、スタックの作成・更新・マージを自動化できる（任意。使わず手動で運用してもよい）。

```text
main ← PR#1 (feat/login-logic) ← PR#2 (feat/login-ui)
```

- **上と下の見方**: `main` に近い方が下の段、遠い方が上の段。上の段は下の段の変更を含む。上の例では、PR#1が下の段、PR#2が上の段。`gh stack view` では、一番上の段が一番上に、`main` が一番下に表示される。
- **マージ順:** 必ず下の段から順にマージする。
- **PR本文:** スタック全体の一覧とこのPRの位置を書く（`gh stack` を使う場合はGitHub上に自動で表示される）。
- **マージ方式:** スタック内はRebase and Mergeを基本とする（`gh stack merge` では `--merge-method` で指定する）。
- **下の段を修正したとき:** 上の段へ反映（rebase）する。
  - `gh stack`: `gh stack sync`（または `gh stack rebase`）
  - 手動: `git rebase --onto <新しい下の段> <古い下の段> <上の段>` のあと `git push --force-with-lease`
- **関連Issue:** `Closes #xx` は最後の段のPRだけに書く。それ以外は `Refs #xx` と書く。原則は [関連Issueの書き方](#関連issueの書き方) を参照。

## 7. hotfix（本番の緊急バグ修正）

本番環境（`main`）の緊急バグ修正は、通常のPRより手順を簡略にしてよい。ただし、CI・テストは省略しない。

- **ブランチ**: `main` から `hotfix/` ブランチを切る（[BRANCHING.md](./BRANCHING.md) 参照）。タイトルは `hotfix: 決済APIのエラーを修正` のようにする。
- **Issue**: 緊急時は、Issueを作る前に修正を始めてよい。事後に必ずIssueを作り、PR本文の `Closes #xx` を書き直す。
- **修正の範囲**: 修正は最小限にする。リファクタリングなど、無関係な変更を混ぜない。
- **レビュー**: セルフレビューは必須。レビュアーの承認待ちは省略してよい（事後に確認を依頼する）。
- **マージ方式**: Squash and Merge を使う（revertしやすいため）。
- **事後対応**: 原因と再発防止を、PR本文の「概要」に1〜2行で書く。
