# 🚀 プルリクエスト規約 (Pull Request Guidelines)

本規約は、コードレビューの負担を減らし、変更の意図と影響範囲をチーム（および未来の自分）に正確に伝えることを目的とする。

## 1. PR作成時の基本ルール

- **1 PR ＝ 1 目的**
  - PRのサイズはできるだけ小さく保つ。「新機能の追加」と「無関係なリファクタリング」は別のPRに分けること。
- **アサインの設定（必須）**
  - PRの責任の所在を明確にするため、作成時は必ず **Assignees に自分自身 (`@me`) を設定**する。
  - レビューが必要な場合は、適切な **Reviewers** を忘れずに設定すること。
- **セルフレビューの徹底**
  - レビューを依頼する前に、必ず自分で「Files changed（差分）」を確認し、不要なファイルやデバッグ用のコード（`console.log` や `dd()` など）が含まれていないかチェックする。
- **タイトルの命名規則**
  - コミットメッセージ規約と同様にプレフィックス（`feat:`, `fix:` など）を使用し、何を変更したかが一目でわかるタイトルにする。
  - 例：`feat: ログイン画面のUI実装`

---

## 2. PRの概要 (Description) とテンプレート

PRの本文は、以下のテンプレート（`.github/pull_request_template.md` に設定推奨）を使用して記載する。

```markdown
## 概要

<!-- 何を、なぜ変更したか -->

## 動作確認

- [ ] Linter・自動テストをクリアした
- [ ] ローカル環境で〇〇が正常に動作することを確認した

## 関連Issue

<!-- Closes #xx -->
```

## 3. マージ方式について

マージ実行時は固定の方式に限定せず、**PRの性質や変更の規模に応じて最適な方式を使い分ける**。

- **Squash and Merge (小〜中規模な機能追加・バグ修正)**
  - **用途:** 細かな作業コミットや試行錯誤の履歴を1つにまとめたい場合。
  - **メリット:** `main` ブランチの履歴が1機能＝1コミットとなり、非常にシンプルで追いやすくなる。

- **Create a merge commit (大規模機能開発・複数人での共通開発)**
  - **用途:** 作業ブランチ内の各コミット履歴（段階的な機能追加やリファクタリングの過程）をそのまま保持したい場合。
  - **メリット:** 変更の意図や過程が細かく残り、後から特定ステップのみを追跡・打ち消し（revert）しやすい。

- **Rebase and Merge (リファクタリング・独立したコミット群)**
  - **用途:** マージコミットを作らず、意味のあるコミット履歴をきれいな一本道（直線状）で残したい場合。
  - **メリット:** コミットグラフが分岐せず一直線に保たれ、全コミットがきれいな履歴として並ぶ。
